- **Next:** [04-sandbox.md](04-sandbox.md) after an explicit yes. Otherwise [05-verify.md](05-verify.md), then [06-evidence.md](06-evidence.md).

```text

```

Show the flow the selected scenarios exercise as one small visual, following [show-me.md](../../straddle-best-practices/references/show-me.md), inline in your reply; write no file. For a SaaS or marketplace plan, it shows the requests as account A and account B and where the account header is sent or omitted, and for every plan, how each outcome arrives through the selected webhook, FIFO, or polling endpoint. Everything it names, participant labels included, comes from what the preview shows: its header lines, the table (its row numbers, and operations, accounts, outcomes and values as the table writes them), and the notification path under it, or, when this run builds no preview, from what the plan says. Copy each outcome exactly as the table writes its `config.sandbox_outcome`, such as `reversed_insufficient_funds`, never a return code such as `R01` or another name for it. Label a participant the preview doesn't name by its role, such as App, not by a name the repository gives it, such as its package name. Show it whether or not this run builds a preview.

When no selected scenario needs a Sandbox write, go to step 5.

Build and ask for approval exactly as in Integrate's [preview step](../../straddle-integrate/steps/04-preview.md). The same table, executing tools, idempotency keys, account rules, and approval rules apply. Integrate's configuration handling does not: when configuration is missing, follow this step's last paragraph, which keeps step 5 and Test's statuses. For Test, the rows are:

- reuse of accounts A and B, and of the customers and paykeys from Integrate, by exact external ID. Create only what is missing.
- a Sandbox paykey for each row of the plan's Bank connection methods table, or, when the plan has no such table, for the method its Decisions log's Bank connection answer gives, and one charge on it: Integrate's paykey for that method reused by exact external ID, or a new one through the row's operation. The developer gives any Plaid or Quiltt Sandbox token; the row names its source, never its value.
- for a Bridge widget method: ask the developer to complete the widget once in their running app in Sandbox, and as which app user. This step sends nothing, including reads. Preview the lookups as rows step 4 runs before the charge: `listCustomers` with `external_id` set to that user's ID, which must return exactly one customer; then `listPaykeys` with that `customer_id`, reading every page, and taking the one returned paykey whose `external_id` equals the one the app stored for that link (`listPaykeys` has no `external_id` filter). The charge's token comes from the app's own code path that charges with its stored encrypted token, or, when the app doesn't keep one, from a `revealPaykey` row through the SDK or CLI. A masked `paykey` from a list or get never goes into a charge. When step 4 finds no match or more than one, it stops and asks; never guess an ID, fake the callback or token, or drive the browser yourself. If the developer skips the widget, record the row `not run: needs the widget completed in a browser`.
- one charge per selected outcome, each with a fresh external ID namespaced by the run ID from [step 1](01-begin.md#run-id), for example `acme-test-<run>-paid-a` for account A and `acme-test-<run>-r01-b` for account B, so each Test run creates new charges and never reuses an earlier run's. Every idempotency key is derived from its row's external ID, so it is new per run too. Within this run, a retry of a row, including the retry scenario and same-key recovery after an unknown result, reuses that row's external ID and key exactly. These charge rows win over any charge row the plan's Future Sandbox writes table fixes: those rows are Integrate's. Use `amount: 10000`, `currency: USD`, `consent_type: internet`, `config.balance_check: enabled`, today's date in US Eastern time as `payment_date` ([Payment dates](../../straddle-best-practices/references/writes-and-approval.md#payment-dates)), and the scenario's `config.sandbox_outcome` from [sandbox-outcomes.md](../../straddle-best-practices/references/sandbox-outcomes.md#states-and-transitions).
- for the customer review and paykey review scenarios, one customer or paykey created with the scenario's `config.sandbox_outcome`, and for the other matrix scenarios, the follow-up rows they name: the review decision, hold, release, cancel, refund, or resubmit. Each create has its own idempotency key and a fresh external ID, and each customer create a fresh email namespaced by run, for example `acme-test-<run>-review@example.com`, because a customer's email is unique on the account ([customers-identity.md](../../straddle-best-practices/references/customers-identity.md)).
- for the dispute and R29 block scenario, its own paykey made from the bank account number step 1 chose for it, shown in the row, and its `failed_not_authorized` charge on that paykey. No other row uses that number, and the dispute charge never uses a paykey from Integrate or another scenario.
- for a `reversed_insufficient_funds` charge, one funding sweep row: `simulateFundingEvent` (`POST /v1/funding_events/simulate`, `funding_event_job_type: charges`) through SDK `client.fundingEvents.simulate` or CLI `straddle funding-events create --funding-event-job-type charges`, for that charge's acting account, with its own idempotency key. It runs at the time [step 4](04-sandbox.md#funding-sweep-for-the-return) gives. The row says the sweep is account-wide, as step 4 describes, so an account nobody else is testing on is safer.
- for the optional Payout scenario, only when the developer approves it: one payout, with no charge for it, on a paykey this run already uses, created with `config.sandbox_outcome: paid` through `createPayout` (SDK `client.payouts.create` or CLI `straddle payouts create`), a fresh external ID namespaced by run such as `acme-test-<run>-payout-a`, its own idempotency key derived from that ID, and the fields in [payouts.md](../../straddle-best-practices/references/payouts.md#what-it-is), for its acting account; then one payouts funding simulation row (`simulateFundingEvent`, `funding_event_job_type: payouts`, through SDK `client.fundingEvents.simulate` or CLI `straddle funding-events create --funding-event-job-type payouts`) with its own idempotency key. That row says the simulation is account-wide, like the charges sweep.
- the retry row, which repeats one create with the identical idempotency key and external ID
- the header-omitted operations the A/B scenario exercises

Name the notification path each status will arrive through, and the wait limit of ten minutes.

The reply that asks for approval has the three parts Integrate's [Ask for approval](../../straddle-integrate/steps/04-preview.md#ask-for-approval) gives, in that order: the whole preview table with the notification path and the wait limit under it, this step's visual right after the table, then the approval question. When you end the turn to wait for the answer, that reply is step 6's closing reply: give all three parts there, after its opening sentences, even if you showed them earlier in the turn, and never point back to a preview above.

When the configuration is missing, the developer says no, or you are ending your turn to wait for an answer, send nothing. Record the Sandbox scenarios as `not run` with the reason (configuration error, denied, or awaiting approval of the Sandbox preview), print `STRADDLE_ABORT` when stopping for configuration or denial, and go to step 5, which still records discovery, then step 6 before ending the turn. A later explicit yes may continue at step 4 only if the exact preview and its environment, base URL, account, operation, and payload remain unchanged; otherwise show a new preview and obtain approval. Step 6 then updates the evidence.
