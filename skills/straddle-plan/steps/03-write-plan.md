# Step 3: Write the plan

- **Needs:** summaries from steps 1 and 2, and the Decisions log and Glossary in `straddle-integration-plan.md`.
- **Tools:** Read, Write, Edit for `straddle-integration-plan.md` only.
- **Next:** [04-review.md](04-review.md).

Print this once, right after reading this file and before reading the template or any reference:

```text
STRADDLE_PROGRESS {"skill":"straddle-plan","step":"03-write-plan"}
```

Fill in `straddle-integration-plan.md` at the repository root from [plan-template.md](../references/plan-template.md). Keep the Decisions log and the Glossary the interview wrote, and change no answer in them: a changed decision goes back to [step 1](01-decisions.md). Replace every other placeholder with evidence, a decision from the log, or `Unresolved`, and use the Glossary's terms throughout. Keep the account scope, notification, lifecycle handling, Sandbox writes, verification, and approval sections even when short. Write `Plan state: Draft`, or `Blocked` when unresolved decisions stop implementation, and `Approval: none`: a new or refreshed plan carries no approval until the developer approves it and step 6 records that.

The plan must cover:

- **Product flow and operations.** Customer, Bridge and paykey, then charge or payout, with the SDK method and API operation for each, citing the matching reference: [customers and identity](../../straddle-best-practices/references/customers-identity.md), [Bridge and paykeys](../../straddle-best-practices/references/bridge-and-paykeys.md), [charges](../../straddle-best-practices/references/charges.md), [payouts](../../straddle-best-practices/references/payouts.md), [refunds and resubmits](../../straddle-best-practices/references/refunds-and-resubmits.md), [ACH timing and consent](../../straddle-best-practices/references/ach-timing-and-consent.md) for `payment_date` and `consent_type`, and [platforms](../../straddle-best-practices/references/platforms.md) on SaaS and marketplace. The customer create sends `phone`, which is required, and says where the app collects it. Each charge create sends the `config.balance_check` the Decisions log records. If a reference can't be read, say which one and mark what it would settle `Unresolved`, rather than filling it from memory.
- **Account scope.** Per operation, whether `Straddle-Account-Id` is sent, required, or omitted for this integration type, citing [account-scope.md](../../straddle-best-practices/references/account-scope.md). For SaaS and marketplace, how the application selects and switches the acting account, and a test that fails locally with zero requests when a required account is missing.
- **Two-account proof (SaaS and marketplace).** Sandbox accounts A and B, a charge or payout for each, evidence that each result belongs to the right account, and evidence that header-omitted calls stayed omitted.
- **Onboarding (SaaS and marketplace).** Two separate items: fast Sandbox account creation through the API for testing, and hosted iframe onboarding with `env=sandbox` and a required `externalId` for the customer-facing flow.
- **Notifications.** The chosen webhook, FIFO, or polling endpoint, created in the dashboard, and its handler as [Endpoint types](../../straddle-best-practices/references/receiving-webhooks.md#endpoint-types) describes: verification, duplicate-safe storage, and acknowledgement or commit for that type. For FIFO, record the body shape the endpoint's transformation produces, from a captured delivery or the dashboard's transformation test output, or mark it open. Cite [notifications.md](../../straddle-best-practices/references/notifications.md) for the choice. No status loop on resource reads.
- **Lifecycle handling.** For each resource in scope, what the app does on every status the notification path delivers, taken from the Decisions log and the "What your app must handle" section of the matching reference: the ones above, plus [returns and disputes](../../straddle-best-practices/references/returns-and-disputes.md) for `reversed` after `paid`, [funding and reconciliation](../../straddle-best-practices/references/funding-and-reconciliation.md) for funding events, and [webhook events](../../straddle-best-practices/references/webhooks.md) for the event per status. Name the decision each row comes from.
- **Future Sandbox writes.** A table of every remote write Integrate or Test will make, each naming its executing tool: the SDK method or CLI command, or a permitted MCP operation. The fourteen operations in [writes-and-approval.md](../../straddle-best-practices/references/writes-and-approval.md) always name the SDK or CLI. Each row lists the environment, account, idempotency key source, external ID, and that it needs a preview and approval. A CLI create row includes `--idempotency-key`, taken from that command's `--help` in the installed CLI; if the installed CLI does not list the flag, the row names the SDK method instead. `--idempotent` never stands in for a key. A charge or payout's `paykey` takes the full paykey token, so include the `revealPaykey` or `getUnmaskedPaykey` row that obtains it, and never write the token itself into the plan. A `reversed_insufficient_funds` test also needs the funding sweep row in Test's [preview step](../../straddle-test/steps/03-preview.md).
- **Files and tests.** Each change names an existing file or a justified new one, the behavior it adds, and the test that proves it. Existing provider code stays unless the developer separately approves a migration.
- **Verification.** The commands the developer can run, and the Sandbox scenarios: one row from the scenario matrix in [sandbox-outcomes.md](../../straddle-best-practices/references/sandbox-outcomes.md#what-your-app-must-handle) for each lifecycle the plan covers, with the `config.sandbox_outcome` to create it with and the transitions to observe. Plan no Sandbox payout, refund payouts included, to reach `paid`, `failed`, or `reversed`: those handlers are tested offline with recorded `payout.event.v1` payloads ([payouts.md](../../straddle-best-practices/references/payouts.md#events-and-sandbox-outcomes)).

**Summary for step 4:** the plan path and each section's status.
